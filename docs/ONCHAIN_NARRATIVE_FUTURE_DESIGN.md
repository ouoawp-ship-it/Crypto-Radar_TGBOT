# 链上叙事雷达后续设计清单

本轮不把 `蒸馏/s5_on_chain_narrative_radar.py` 合并到现有
`paopao_radar/onchain_flow/`。该参考脚本只用于提炼需求，不能直接复制其
独立 Telegram、数据库、非稳定接口和主观判断。

未来进入独立评审阶段时，至少满足以下边界：

1. 使用独立模块、独立进程、独立 `data/onchain_narrative/` 数据目录和独立
   Telegram topic，不与现有 Base CEX 流入流出进程、数据库、游标、状态文件、
   outbox 或冷却记录混写。
2. 配置入口为 `ONCHAIN_NARRATIVE_ENABLE=false`，默认 dry-run；真实 Telegram
   继续要求现有 `--send --confirm-real-send` 双重门禁。
3. GMGN、DEX 或其他第三方接口接入前，先完成服务条款、授权方式、字段语义、
   稳定性、更新频率、请求限流、缓存和故障降级验证。
4. 不复制名人关键词、主观叙事标签、未经验证的“安全”判断或确定性涨跌措辞。
   叙事只能是有来源和时间戳的上下文，不得单独生成交易方向。
5. 新币资产必须以 `chain + contract` 作为唯一身份；symbol 仅用于展示，不能
   用于去重、合并或持久化主键。
6. 候选进入信号层前必须具备流动性、持币集中度、合约风险、重复地址检测、
   冷却、幂等键和字段级数据来源；字段缺失要显式降级，不能猜测。
7. 数据采集、规范化、风险策略、评分、通知分别设计为可测试的小模块；所有
   外部请求可注入、可 mock，具备有限超时、有限重试和速率预算。
8. 先以固定夹具和历史回放验证误报，再进行隔离 dry-run；不得在验收前启动
   systemd 服务或真实发送。

后续建议的最小纵向切片是：

`DEX 新池事件 → chain+contract 规范化 → 流动性/集中度/合约风险门禁 →`
`叙事上下文 → 独立 SQLite 审计 → 独立 Telegram dry-run`
